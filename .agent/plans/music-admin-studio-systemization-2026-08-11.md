# 后台音乐策展工作台体系化方案

日期：2026-08-11
范围：`apps/admin`、`apps/server-go`、`packages/types`、数据库迁移与真实浏览器验证

## 1. 目标

把当前“曲库 + 歌单 + 展示设置”的功能集合，升级为一套可持续维护的音乐策展系统。管理员应能从原始音频出发，完成：

`媒体入库 → 元数据修正 → 标签归档 → 喜爱收藏 → 歌词上传/校正/绑定 → 封面替换/生成 → 歌单编排 → 公开发布 → 完整度复核`

目标不是复制 Apple Music 的品牌视觉，而是达到同等级别的产品完整度、状态可信度、操作反馈和跨端细节。

## 2. 已确定设计

### 2.1 信息架构

后台音乐模块收敛为五个一级工作区：

1. **策展总览**
   - 展示曲库总量、收藏、歌词就绪、缺封面、已打标签、公开歌单等指标。
   - 用“策展信号链”展示每个环节的完成率，而不是只展示孤立数字。
   - 提供跳转到缺歌词、缺封面、未打标签、收藏曲目等明确入口。
2. **歌曲库**
   - 搜索、分页、状态、收藏、标签、歌词状态、封面状态筛选。
   - 单曲编辑负责元数据、喜爱状态、标签、封面和歌单归属。
   - 列表直接显示策展完整度，避免逐首点开排查。
3. **歌词工作台**
   - 歌词作为独立资产，可上传 `.lrc` / `.txt`、创建空白稿、校正时间轴、维护语言与审核状态。
   - 歌词可以绑定、解绑或重新绑定到歌曲。
   - 绑定关系和歌词内容必须由服务端保持一致，不能只依赖前端文本框。
4. **歌单策展**
   - 保留现有创建、排序、公开、试听能力。
   - 增加喜爱歌单、封面直传/生成、策展状态反馈。
5. **展示与播放**
   - 保留公开播放器、默认歌单、播放策略和皮肤配置。
   - 只承载发布与播放预览，不再混入曲库维护动作。

### 2.2 领域模型

- **歌词资产 `music_lyrics`**
  - 独立 ID、名称、内容、格式、语言、来源文件名、时间偏移、审核状态。
  - 与歌曲保持至多一对一绑定；歌词可处于未绑定状态。
  - 历史 `music_tracks.lyric` 数据迁移为独立歌词资产。
- **喜爱收藏**
  - 歌曲和歌单分别保存 `is_favorite`。
  - 收藏是策展维度，不等同于公开、精选或播放次数。
- **标签**
  - 复用已有 `media_tags` / `media_file_tags`，避免音乐标签和媒体标签产生双份真相。
  - 音乐 API 聚合音频媒体上的标签，并支持按标签筛选曲库。
- **完整度**
  - 服务端提供可统计的缺歌词、缺封面、未打标签、收藏数量。
  - 前端按元数据、封面、歌词、标签、歌单归属计算单曲策展状态。

### 2.3 视觉方向

主题对象：AetherBlog 的独立内容策展者。
页面唯一任务：把原始音频变成可公开发布、信息完整的音乐作品。

#### 色彩

- `Void Ink #111318`：封面与播放舞台的深背景。
- `Signal Rose #EC496F`：收藏、当前播放和主要策展动作。
- `Lyric Cyan #4CC9D8`：歌词时间轴与校正状态。
- `Archive Violet #7868E6`：标签与归档关系。
- `Ready Green #45B782`：策展完成和可发布状态。
- `Paper Mist #F4F6F8`：亮色管理表面。

生产 UI 优先消费现有 `--bg-*`、`--ink-*`、`--aurora-*`、`--signal-*` 设计令牌；上述十六进制主要用于生成式封面算法与设计样稿。

#### 字体

- 展示标题：沿用后台现有标题字体与字重系统，不引入新的网络字体。
- 正文与表单：沿用后台正文系统。
- 时间轴、时长、完整度、偏移量：使用现有等宽数字类 `tnum` / `font-mono`。

#### 视觉签名

**策展信号链**是唯一强记忆点。每首歌用六段微型轨道显示：

`元数据 / 封面 / 标签 / 歌词 / 歌单 / 发布`

完成项发光，缺失项保持低对比并可点击定位。它编码真实管理流程，而不是装饰性进度条。

### 2.4 生成式封面

- 生成式封面采用“共振地图”算法：以歌曲标题、艺术家或手动种子生成可复现的谐波环、流场轨迹和微粒密度。
- 相同种子与参数必须生成完全相同的结果。
- 管理员可以调整密度、扰动、轨道数和三色调色板。
- 预览在浏览器内生成，应用时渲染为 PNG 上传到媒体库，再通过现有 `coverMediaFileId` 绑定。
- 不在生产包内引入 p5.js；交互研究样稿使用 p5.js，生产实现使用延迟加载的原生 Canvas 模块。

## 3. 合理推导

1. “喜爱收藏”按管理员策展收藏实现，而不是立即引入访客账号级收藏。当前公开博客没有与本目标匹配的用户收藏身份模型。
2. 音乐标签复用媒体标签，因为每首曲目已有唯一 `media_file_id`，复用能保持媒体库与音乐后台一致。
3. 歌词绑定采用独立资产，而不是继续扩展 `music_tracks.lyric` 文本字段；否则无法实现未绑定歌词、重新绑定、来源文件和审核状态。
4. 生成式封面先作为管理员工具，不自动覆盖现有封面；任何替换都必须由用户显式应用。
5. “Apple Music 级”以产品闭环、视觉层级、响应反馈、无障碍和跨端质量验收，不以像素复刻第三方产品。

## 4. 待评审问题

以下问题不阻塞本轮实现，但需要后续产品决策：

1. 是否需要访客账号级“喜欢/收藏”，以及是否与管理员策展收藏分离。
2. 一首歌是否需要支持多语言、多版本歌词同时存在；本轮先实现一个活动绑定歌词 + 任意未绑定歌词资产。
3. 是否需要 AI 自动对齐歌词时间轴；本轮先提供确定性的偏移、标准化和格式校验。
4. 是否需要专辑作为独立实体；本轮继续保留歌曲上的专辑文本。
5. 是否需要把生成式封面参数持久化，以便日后重新编辑；本轮持久化最终 PNG，参数仅在生成会话中存在。

## 5. 用户旅程

### 5.1 歌词上传与绑定

> 作为管理员，我希望上传一份 LRC，先检查时间轴并修正偏移，再绑定到正确歌曲，以便公开播放器稳定展示同步歌词。

验收：

- 支持 `.lrc` / `.txt`，限制大小并给出编码错误提示。
- 上传后成为独立歌词资产，不要求立即绑定。
- 可查看时间轴行数、纯文本行数、异常时间行数。
- 可整体前移/后移时间轴并标准化时间戳。
- 可绑定、解绑、重新绑定歌曲。
- 绑定后曲库和公开播放器读取同一歌词真相。

### 5.2 标签与收藏

> 作为管理员，我希望给歌曲打上风格、场景或情绪标签，并把重点歌曲收藏起来，以便快速构建歌单。

验收：

- 单曲编辑内可添加、移除、创建标签。
- 曲库可按单个标签和收藏状态筛选。
- 收藏按钮具备乐观反馈与失败回滚。
- 曲库列表直接显示标签，不需要进入媒体库查找。

### 5.3 封面替换与生成

> 作为管理员，我希望从媒体库选择、直接上传或生成封面，并在保存前预览，以便每首歌和歌单都有稳定的视觉身份。

验收：

- 现有媒体库选择保留。
- 支持直接上传图片并立即选中。
- 支持可复现的生成式封面预览、随机种子和 PNG 应用。
- 清除、替换与取消不误删媒体文件。

### 5.4 策展诊断

> 作为管理员，我希望立即知道哪些歌曲还缺歌词、封面、标签或歌单归属，以便按优先级补齐。

验收：

- 总览显示服务端统计值。
- 曲库行展示策展信号链。
- 点击缺口入口能进入带筛选条件的曲库或歌词工作台。
- 空状态明确告诉管理员下一步动作。

## 6. 技术实施顺序

1. 新增迁移与共享类型。
2. 扩展 Go repository / service / handler，并写 sqlmock 回归测试。
3. 提取歌词解析、标准化、偏移和完整度纯函数，先写 Vitest。
4. 新增歌词工作台与服务层。
5. 接入媒体标签、收藏与筛选。
6. 新增延迟加载的生成式封面工作室。
7. 重排五工作区导航和总览。
8. 完成桌面、390px 移动端、键盘、Reduced Motion 与错误路径验证。
